---
description: Continue a Fashion project from its saved state.
disable-model-invocation: true
---

1. If `.fashion/state.json` is missing, tell the user to run `/fashion:start`. Stop.
2. Load the current `fashion:fashion` skill before interpreting saved state. Read `.fashion/state.json`, `.fashion/brief.md`, `ux/decisions.md` (if present), and the tail of `research/competitors.md`.
3. Say in three lines: current phase, what is done, what is open.
4. Do not assume a saved task is alive or dead after restart. Inspect task status and any command it started before replacing it. If phase is 2 and `researcherDone` is false, ask before relaunching the researcher (it appends to the existing file; tell it what is already there). Same for `analystDone`.
5. If phase is 4, read `tickets/board.md` and each unfinished `tickets/<id>/state.json`, including `blocked` tickets. Validate the exact state contract in the current skill. Reconcile attempt, task ID, branch/worktree, built commit, merge commit, and checked commit with Git and result/check files. Resume the first incomplete stage: collect current-attempt results, skip an already landed merge, and check only the current commit. Ignore stale results from older attempts. Do not relaunch while a task or worktree is still active. If an old project has missing or invalid state, preserve the original as `state.legacy.json`, infer a valid stage from Git and files once, and write only the documented fields. A legacy `checked` stage with failed or unrun items becomes `blocked`, never `done`. If evidence is insufficient, keep it `blocked` and record why in `log.md`. Restart the watchdog schedule if any ticket remains active.
6. Reassess old blockers using current workflow rules. A Responsively-only restriction inherited from an older plugin, board, or check report is superseded by the current fallback rule: try an available capable real browser before asking the user. Preserve an explicit project-specific restriction the user deliberately imposed; distinguish it from copied plugin policy. Record the migration and retry plan in `log.md`. Do not repeat a landed merge or rebuild code just to rerun a previously unsupported check.
7. Before proposing or dispatching a resumed browser check, explicitly include the `/fashion:setup` readiness probe in the resume plan. Identify the app working directory from `result.md` (for example `site/`), then verify the actual runtime there: module resolution, browser launch, required keyboard interactions and saved screenshots. A machine-level CLI version or a probe in another directory does not count. If readiness is unknown, run the probe before launching a checker; a blocked ticket stays `blocked` during this step. If it fails, record the dependency/capability gap and resolve tooling without incrementing the implementation attempt or dispatching a reproducer. A global runtime counts only when named with `FASHION_PLAYWRIGHT` and passed; then save the probe's JSON line in `.fashion/browser-runtime.json` and pass its record path and `invocation` to the checker. Reuse a record already passed in this resume for the same `appDir` when its `modulePath` and version still match.
8. Clean up after dead tasks: run `node "${CLAUDE_PLUGIN_ROOT}/scripts/owned-process.mjs" list --root <root>`. For each record still `running` whose owning task you confirmed terminated, run `stop` for that owner, role and attempt, and dispatch its replacement only after exit 0. Leave processes of tasks that are still active. On exit 4 (`identity-mismatch`, `unverified`, `inspection-failed`, `still-running`) leave the processes and the record alone, keep the ticket `blocked` and report it. Never stop a process because it holds a port the app uses.
9. Before continuing any phase, if `siteType` is missing or null, infer it from the brief and existing screen scope (`landing` or `multi`); ask once if unclear, then save it. This includes 0.4.0 projects that already have `screens`, and earlier projects resumed before phase 4. Keep existing screen IDs, tickets, accepted decisions and active tasks; do not recreate screens just to set site type. Populate `siteUrl` from an explicitly identified own-site URL when available, otherwise leave it null; this does not grant permission to reuse assets.
   Screens (phase 4). If `.fashion/state.json` has no `screens` (a project from plugin 0.3.0 or earlier), migrate once before assigning anything:
   - Copy the current state to `.fashion/state.pre-screens.json`. Set `siteType` from the brief (`landing` or `multi`; ask if unclear). Build the screen list from the brief's journey and `ux/decisions.md`: one `landing` screen for a landing page, otherwise home or the entry screen first and the rest `planned` with no fixed order, and map every existing ticket to one screen (foundation tickets to the first). Add the `screen` column to `tickets/board.md`.
   - Keep every ticket's state, attempt, task, branch and commits as they are. Do not rerun foundations or any done ticket.
   - No screen becomes `accepted` by migration: finished work still needs its critique and the user's answer. A screen whose tickets are all `done` starts at `building` and goes to step 4 of 4.3; `currentScreen` is the first screen in order that is not `accepted`.
   - If the order or a ticket's screen is unclear, show the proposed order and mapping and ask the user once before writing.
   - Write the migration once and log it; a later resume that finds `screens` does not migrate again.
   Then continue with `currentScreen` exactly as "A restart never skips the critic" in 4.3 says. Never start tickets for another screen.
10. Continue the current phase from where it stopped. Do not repeat confirmed steps. For a surviving active task, retain its task ID; a second resume must not launch a duplicate.
